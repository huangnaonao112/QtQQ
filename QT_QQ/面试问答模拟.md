# QtQQ 面试问答模拟（按真实面试顺序）

> 模拟真实面试：面试官拿着你的简历和 GitHub 仓库，从上往下问。
> 答案是第一人称的口述版本，照这个说就行，不要背成文档腔。
> 所有数字、文件名、坑都与仓库真实代码一一对应，可以放心展开。

---

**Q1：简历上写"自研局域网 IM + AI 助手"，先花两分钟整体介绍一下这个项目。**

这是一个三进程的局域网聊天系统。客户端是 Qt Widgets 加 WebEngine 做的聊天界面，服务端是消息转发中枢，监听 57777 端口，所有客户端和 AI 机器人都用 TCP 连它。通信协议是自定义的 NDJSON——每条消息一行 JSON 加一个换行符。AI 助手是一个没有界面的独立进程，以一个普通账号的身份登录服务端，群里 @ai 或者私聊它，它就调智谱 GLM 的接口回答，还能通过 function calling 去查 MySQL 里真实的员工和部门数据。三个工程在三个独立 git 仓库里，只共享协议和数据库。数据库是 MySQL 8.0，消息全部落库，支持历史拉取和离线私聊补发。整条链路我写了一个 PowerShell 回归脚本，七项检查逐项 PASS/FAIL。

---

**Q2：这个项目是你从零写的吗？还是跟着课程做的？**

基础界面框架来自一个课程的局域网聊天 demo，这部分我如实说。但我在它上面做的扩展是主体：整个通信协议是重新设计的，服务端的消息投递从 UDP 广播重构成了 TCP 按连接单播，加了握手登记、私聊定向投递、离线补发、消息落库、历史拉取；AI 机器人整个是我从零写的，包括智能体循环和 SSE 流式解析；另外修了一批课程原代码里就存在的 bug，比如长消息气泡不换行、大账号 int 溢出。我认为判断一个人是否真的做过项目，不是看起点，而是看他能不能讲清楚每个设计决策的为什么，以及踩过什么坑——这几个我都能展开讲。

---

**Q3：为什么拆成三个独立进程、三个独立仓库？**

客户端、服务端、机器人职责完全不同：客户端是 GUI，服务端是长驻的转发中枢，机器人要发起外网 HTTPS 调大模型。拆开之后故障隔离是天然的——机器人挂了或者调大模型超时，完全不影响正常聊天；服务端升级也不用动客户端。三个仓库互不依赖代码，只共享两样东西：协议和数据库表结构。协议演进的时候，比如我给流式回复加 reset 字段，客户端和机器人分开发版，服务端甚至不用改，因为它是"收到一行 JSON 就转发"的哑转发模型，不解析业务。

---

**Q4：通信协议是怎么设计的？为什么选 NDJSON？**

每条消息是一行紧凑 JSON 加一个换行符，方向用 what 字段区分：hello 握手、history 拉历史、msg 普通消息、file 文件、msg_stream AI 流式增量。msg 里面 type 0 是群聊、1 是单聊，recv 是群号或对方账号，msg 字段是二维数组，支持一条消息里混文本和表情块。选 NDJSON 而不是长度前缀或者 protobuf，主要有三个原因：换行符天然做消息边界，实现简单；JSON 人类可读，用 telnet 或者脚本就能直接调试协议；WebEngine 里的 JS 原生能解析。代价是 JSON 比 protobuf 冗余，但对一个局域网十几人规模的 IM 来说带宽不是瓶颈，可调试性更重要。

---

**Q5：TCP 粘包是怎么处理的？**

TCP 是字节流没有消息边界，这个问题躲不掉。我踩过的具体坑是大文件传输：文件 base64 之后整文件塞进一条 JSON，5MB 的文件会被 TCP 拆成几十个分段到达，最早的实现是每次 readyRead 直接 split('\n')，结果半个 JSON 被当成一条完整消息转发出去，接收端全是解析失败。修复是两端都改成半包缓冲：每次 readyRead 把数据 append 到这个连接自己的 m_buf 里，然后循环找换行符，只处理完整行，剩下不完整的留在缓冲区等下一个包。另外加了防护：单连接缓冲超过 8MB 直接断连，防止恶意灌包把服务端内存吃光。

---

**Q6：服务端怎么知道哪条 TCP 连接是哪个用户的？私聊怎么路由？**

靠握手。客户端连上后第一行必须发 hello，带上自己的账号和角色；服务端用一个 QHash<QTcpSocket*, QString> 建立"连接到账号"的映射，断开时同步摘除。私聊投递就是拿 recv 账号反查这个映射，找到该账号名下的所有连接逐个写出去——同账号多开也支持。这里有个前置问题：早期服务端是"收到就广播给所有人"的模型，私聊等于被所有人看见，这就是我必须做 hello 握手的原因。还有个坑：历史请求必须在 hello 之后发，因为私聊历史要按登录身份查库，顺序反了服务端不知道你是谁，我把这个顺序约束写在了客户端的连接状态机里，连接建立先补发 hello，再补发挂起的 history 请求。

---

**Q7：离线消息是怎么做的？**

消息转发的同一步就落库，写进 tab_messages 表，私聊消息多一个 delivered 标记，0 表示收件人还没收到。收件人下次 hello 上线的时候，服务端查这个表，把他所有 delivered=0 的私聊补推过去，然后置 1。历史拉取也是查同一张表，客户端打开聊天窗时发一个 history 请求带对方 ID 和条数，服务端按时间升序回包，客户端只渲染不回发，所以不会重复。为什么全量落库：服务端重启、客户端重开都不丢消息，离线补发和历史拉取两个功能都建立在它上面。

---

**Q8：听说你把 UDP 广播重构成了 TCP 单播？为什么？**

这是我印象最深的坑。最早的版本消息投递用的是 UDP 广播：服务端 writeDatagram 到 255.255.255.255 的 59999 端口，客户端 bind 同端口接收。局域网两台真机没问题，但我同机开两个客户端加机器人测试的时候，出现私聊随机丢消息。排查发现 Windows 下多个 socket 用 SO_REUSEADDR 绑定同一个 UDP 端口，广播包只会投递给其中一个——互相抢包。为了确认，我写了一个独立的 UDP 监听探针，果然三个监听者只有拿到包的那个能收到。修复就是把投递整体迁到 TCP：利用 hello 建立的连接注册表，收到消息后逐连接单播。TCP 点对点，每个客户端都能收到，而且天然有序可靠。UDP 接收路径我保留做兼容，但主链路全是 TCP 了。这个事给我的教训是：SO_REUSEADDR 在 Windows 上的语义和 Linux 不完全一样，不能想当然。

---

**Q9：服务端怎么应对慢客户端和高并发？**

并发模型上，QTcpServer 本身是事件驱动的，单线程管所有连接，没有 accept 阻塞也没有每连接一线程的开销，十几人的局域网规模完全够。慢客户端用背压保护：往某个连接 write 之后如果 bytesToWrite 积压超过 1MB，说明这个客户端收不动了，这条消息直接跳过并打日志——聊天消息可以丢，但服务端不能被一个慢客户端拖垮。另外加了单连接缓冲 8MB 上限的防护。诚实的短板是：没有做线程池，所有连接共享一个事件循环，CPU 密集的操作会阻塞所有人；要上生产的话消息加解密和落库应该挪到工作线程。这个我是主动说的，面试官问"能不能扛高并发"的时候，说"目前的设计上限在哪、怎么演进"比吹数字可信。

---

**Q10：断线重连是怎么做的？**

三层自愈。第一层心跳：客户端和机器人各有一个 5 秒定时器检查连接状态，UnconnectedState 就重新 connectToHost。这个主要是给机器人加的——机器人是被动接收方，不主动发消息就永远没有重连时机，服务端一重启它就静默失联，这是我实际踩过的坑。第二层发送自愈：发消息时发现没连上，先 abort 旧连接再带 2 秒超时重连，连上照发。第三层是请求兜底：没连上时发的 history 请求先存在 pending 队列里，connected 回调里补发，并且保证 hello 在 history 前面。这三层组合起来，服务端重启之后十几秒内所有端自动恢复，不需要人为干预，这个场景也写进了 e2e 回归脚本。

---

**Q11：客户端的聊天界面为什么用 WebEngine？不重吗？**

重，但我认为值得。消息气泡需要富文本排版、表情图混排、任意样式组合，用原生控件要么 QRichTextControl 定制成本很高，要么效果糙。WebEngine 方案是气泡用 HTML 模板加 CSS 渲染，改样式只需要动 CSS。C++ 和页面通过 QWebChannel 双向通信：C++ 收到消息用 runJavaScript 调页面里的 JS 函数插气泡；用户点表情、点发送，JS 又通过 channel 对象调回 C++。成本是进程里多了一个 Chromium 内核，内存占用大，而且带来一堆环境问题——这个我有实战（下一题展开）。如果重新选型，QWebEngineView 依然是首选，但我会更早把资源加载策略设计好。

---

**Q12：WebEngine 这条路上你踩了哪些坑？**

三个印象深的。第一是路径：exe 放在含 "c++" 的目录下，页面的 file:// URL 在 WebEngine 里有兼容问题，页面直接停在 about:blank；解决办法是把页面和动态脚本都写到无特殊字符的临时目录再加载。第二是缓存：动态生成的 JS 被引擎缓存，落盘更新了页面加载的还是旧版，导致新的流式逻辑永远不生效——排查了很久，最后在生成 HTML 时给脚本引用加时间戳参数防缓存。第三是安全策略：QWebEnginePage 的 acceptNavigationRequest 默认拦掉非 qrc 的导航，页面改从磁盘加载后导航全被吞，还有 LocalContentCanAccessFileUrls 这类设置，一个没开就是"页面白屏但无报错"。这几个坑的共同点是静默失败，后来我把 WebEngine 的控制台输出桥接到 qDebug，才让这类问题可见。

---

**Q13：AI 助手是怎么"接进"聊天系统的？**

机器人是一个无界面的 console 进程，本质上是一个没有 UI 的特殊客户端：同样的 TCP 连上去、发同样的 hello、走同样的协议，只是角色标记为 bot。收到消息后的处理分两层：先做意图和过滤——群聊必须带 @ai 唤醒词才响应，私聊直接响应；然后进入智能体循环调大模型。回复按普通消息协议发回服务端转发，所以对群里其他成员来说，AI 就是一个叫"AI助手"的普通账号在说话。防自激是关键设计：服务端转发不区分来源，机器人自己发的消息也会广播回来，不过滤就是自己回答自己死循环，所以 send 等于自己 ID 的消息在入口直接丢弃。

---

**Q14：function calling 是怎么实现的？模型怎么"查数据库"？**

这是我最想展开讲的点。我在机器人里做了一个 ToolRegistry 工具注册表，每个工具是"名称 + 描述 + JSON Schema 参数定义 + 执行器"。请求大模型时把工具列表一起发过去。模型不直接回答，而是返回 tool_calls——函数名和 JSON 参数；机器人本地执行真实查询，我注册了三个工具：按部门查员工、列所有部门、按关键字查员工详情，底层是 QSqlQuery 预编译查询；然后把查询结果以 role 为 tool 的消息回喂给模型，模型基于真实数据组织自然语言回答。整个过程是个循环，我限制了最多四轮防止模型反复调工具。实测效果：群里发"@ai 人事部有哪些人"，模型返回 tool_calls 查询人事部，回答"人事部有 10001 renyi、10002 rener"——数据是真实从 MySQL 查出来的，不是模型编的。扩展新工具就是写一个函数加一行注册，模型侧零改动，这是 function calling 相对关键词路由的本质优势。

---

**Q15：function calling 实际调起来稳吗？有什么经验？**

有两个实测经验。一是模型不一定触发工具：glm-4-flash 对"人事部有哪些人"这种问题，只给 tools 参数时它第一次直接礼貌地拒绝说"我无法访问内部数据"。在 system prompt 里加了"凡涉及查询公司员工/部门/组织信息的问题，必须调用提供的工具，不要编造"之后才稳定触发。所以提示词工程和 API 参数要配合着调。二是流式模式下 tool_calls 是分片到达的：arguments 字符串被切成多段，要按 index 聚合拼接完才能解析，我的 SSE 解析器专门处理了这个。另外所有查询用 prepare 加 bindValue 占位符，全项目没有一处字符串拼 SQL。

---

**Q16：流式输出（打字机效果）是怎么实现的？**

三层配合。LLM 客户端层解析 SSE：响应体是 "data: {...}" 逐块返回、以 [DONE] 结束，我维护一个跨 readyRead 的行缓冲做粘包处理，解析出增量文本。智能体层做节流：模型每吐一个 token 就发一条消息会把聊天列表刷爆，我用 400 毫秒的定时器把增量聚合起来批量推。渲染层是前端：页面里的 streamAppend 函数按发送者 ID 把增量追加到同一个气泡里，消息结束收到 done 标记就销毁气泡句柄。另外做了"正在思考中"的即时反馈：收到问题的瞬间先推一条占位文本，首段真实内容到达时带 reset 标记，前端清空占位再写入正式回答——用户体感是立刻有响应，而不是盯着空白等两秒。

---

**Q17：机器人的上下文和并发是怎么管理的？**

两个实测得出的规则。第一，上下文只存用户问过什么，不存 AI 答过什么——这是我真实踩的坑：早期把答案也存进上下文，模型在多轮对话里会把之前查询过的旧名单当成当前事实复述出来，数据是错的。只存问题之后，每轮工具查询的结果都是新鲜的。第二，并发串行化加排队：智能体内部状态（消息数组、轮次、回复目标）不是线程安全的，我用一个 m_busy 标志做单飞，忙的时候新请求进 QQueue 排队而不是丢弃，队列上限 20。另外回复目标是一个 ReplyTarget 对象随请求按值传递，而不是存在成员里——否则并发的私聊请求会把群聊的回答改发到私聊窗口，这个我也是真实踩过的。

---

**Q18：SQL 注入怎么防的？**

全项目数据库访问统一用 QSqlQuery 的 prepare 加 bindValue 占位符，没有任何一处字符串拼接。早期的登录查询是 QString 拼接的，账号框输入 "1001 OR 1=1 --" 就能绕过密码，我重构时全部换成了占位符。机器人的查询工具还多一层约束：只读不写，参数经过 JSON Schema 声明，模型返回的参数先过 QJsonDocument 解析校验，解析失败就把错误信息回喂给模型让它自己纠正。

---

**Q19：讲一个你印象最深的 bug。**

讲一个链条最长的。现象是 AI 机器人在群里有时回复有时不回，私聊完全没反应。我按链路分层排查：先给服务端加了文件日志——这里有个前置问题，服务端是 GUI 程序没有控制台，qDebug 输出完全丢失，我用 qInstallMessageHandler 把日志落文件才看到内部状态；日志显示服务端收到消息、转发了，正常。再给机器人加收包日志，也正常收到消息、发起了 LLM 请求。唯独没有"回复发出"的痕迹。最后在发送函数里加字节级日志，才发现这个函数体在多轮补丁中损坏了——JSON 的 write 语句整个丢失，只剩下写换行分隔符的那一行，所以机器人每次"发消息"实际只发出一个孤零零的换行符，服务端按行拆分时空行被跳过。修复本身很简单，但教训很深：多轮自动化补丁叠加会静默破坏源文件，之后我改用编辑工具逐处修改并且每步用 git diff 核对；另外关键发送路径必须有日志，这次能定位全靠之前铺的可观测性。

---

**Q20：还有什么印象深的 bug？**

一个是 int 溢出。我的测试账号是 2652344414，超过 int 上限 21 亿，toInt 之后变成负数。这个负数被拼进了前端动态生成的 JS 变量名里——"var external_-1642622882"不是合法标识符，整个脚本文件解析失败，页面上所有 AI 相关函数静默消失。这类 bug 的隐蔽点在于失败是无声的：JSON 正常、流程正常，只有浏览器控制台里有报错。我把 WebEngine 控制台消息桥接到 qDebug 之后才看到，修复是所有动态生成的 JS 名统一净化掉负号，并且生成、注册、调用三处用同一套规则。另一个是类型问题：协议里 type 字段是数字，我用 toString 去取，QJsonValue 对数字返回空串，导致私聊消息全被当成未知类型丢弃——教训是读 JSON 字段要用和写入一致的类型方法。

---

**Q21：这个项目怎么测试的？**

三层。最上面是端到端回归：一个 PowerShell 脚本按顺序拉起服务端、机器人、两个不同账号的客户端，然后逐项验证——服务端转发、机器人应答、两账号互发、AI 私聊、消息落库、离线私聊补发、服务端重启后自动重连，每项打印 PASS/FAIL，退出码非零表示有失败，跑一遍两分钟。中间是机器人的测试钩子：--selftest 做分层自检，不依赖任何客户端，依次验证数据库查询、工具注册表执行、LLM 非流式、LLM 流式，每层 PASS/FAIL；--echo 是协议回环模式，收到什么回什么，专门隔离验证收发链路而不碰大模型。最底下是客户端的 --autotest 参数，自动登录、自动打开指定聊天窗、自动发指定消息。这套东西是被逼出来的：早期我靠"重启全家桶看日志"调试，效率极低，后来把每个环节都做成可独立触发、可断言的，排查效率完全不一样。

---

**Q22：Qt 的信号槽和事件有什么区别？你在项目里怎么用的？**

事件是系统派发的，比如鼠标键盘，走的是 accept/ignore 和冒泡链；信号槽是对象主动发出的通知，是松耦合的回调机制。项目里两者都有典型场景：无边框窗口拖动用的是事件——TitleBar 重写 mousePress/Move/Release，用 globalPos 算位移调 move；中间还处理过一个双重的坑，TitleBar 和基类各处理一次鼠标事件导致窗口抖动，通过 accept 截断冒泡解决。网络收发全走信号槽：readyRead 触发解析，解析完 emit 一个带业务数据的信号给上层，协议层和业务层完全解耦。跨线程的场景上，QNetworkReply 的 finished 回调和 socket 信号都在主线程事件循环里，所以我的异步回调链虽然跨了多个异步边界，但都在同一线程，用的是按值捕获状态而不是加锁。

---

**Q23：单例为什么用 Q_GLOBAL_STATIC？**

手写单例要处理三件事：懒加载、线程安全、程序退出时的析构。Q_GLOBAL_STATIC 一行宏全解决：第一次调用才构造，内部用原子操作保证多线程下只创建一份，进程退出自动析构。项目里 UseMySQL、WindowManager、NotifyManager 都是这么做的。还有一个相关的坑：跨异步回调链的状态捕获——我的自检代码里 lambda 链跨了三个异步边界，中间层按引用捕获了外层栈上的变量，外层返回后就是 use-after-free，进程无声退出。修复是跨异步边界的状态全部用 shared_ptr 或者按值捕获。这个我总结成一条自己的规则：异步回调一律按值持有状态，引用捕获只用于确定存活的对象。

---

**Q24：数据库连接为什么做成单例？**

QSqlDatabase 建立连接有真实的 TCP 握手和认证开销，而且 Qt 文档明确不建议反复 addDatabase 同名连接——会打重复连接警告并覆盖旧连接。所以服务端、客户端、机器人各自持有一个全局连接，整个进程复用。查询全部走预编译占位符。客户端这边有个诚实的架构妥协：基础通讯录数据仍然直连 MySQL，理想架构是这些也走服务端接口，让服务端独占数据库——这个我在笔记里标注为改进项。

**Q25：这个项目目前有哪些不足？如果要继续演进，你会怎么做？**

主动说四条。第一，安全：TCP 明文传输，send 字段客户端自填可冒充，生产要上 TLS 加 token 鉴权。第二，架构：客户端还直连数据库读通讯录，应该全部收敛到服务端接口。第三，规模：服务端单事件循环，没压测过，演进方向是读写分离到工作线程、落库异步化。第四，AI 部分：会话上下文只存了问题没存答案（这是有意为之，模型会复述旧数据），多轮对话体验有上限，演进方向是把工具查询结果做成结构化的短期记忆。文件传输目前是 base64 整文件塞一条 JSON，上限 5MB，分块传输在待办里。说这些是想表明：我知道当前设计的能力边界在哪，也知道往哪走。
